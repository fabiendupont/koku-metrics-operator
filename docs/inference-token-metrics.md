# Inference Token Metrics Collection

## Overview

The koku-metrics-operator collects inference token usage
from LLM serving endpoints running on OpenShift AI (RHOAI).
This enables Red Hat Cost Management to track and bill LLM
inference consumption per tenant.

The operator supports three metric sources and uses automatic
fallback: vLLM-native metrics are tried first, then OTel
GenAI standard metrics, then Kuadrant identity-based token
metrics if neither vLLM nor OTel GenAI is available.

## Metric Sources

### vLLM-native (primary)

| Metric | Prometheus source | What it measures |
|--------|------------------|------------------|
| Input tokens | `vllm:prompt_tokens_total` | Tokens in the prompt sent to the model |
| Output tokens | `vllm:generation_tokens_total` | Tokens generated by the model |

Grouped by `pod`, `namespace`, `node`, `model_name`, and
`inference_service` (from KServe pod label).

**Prerequisites:**
- vLLM deployed via OpenShift AI (RHOAI) model serving
- vLLM Prometheus metrics endpoint enabled (default)
- Prometheus scraping vLLM pods via ServiceMonitor

### OTel GenAI standard (fallback)

| Metric | Prometheus source | What it measures |
|--------|------------------|------------------|
| Input tokens | `gen_ai_client_token_usage_sum{gen_ai_token_type="input"}` | Input tokens per OTel GenAI convention |
| Output tokens | `gen_ai_client_token_usage_sum{gen_ai_token_type="output"}` | Output tokens per OTel GenAI convention |

Grouped by `pod`, `namespace`, and `gen_ai_request_model`.

These metrics follow the [OpenTelemetry GenAI Semantic
Conventions](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-metrics/)
(`gen_ai.client.token.usage` histogram). Sources include:

- **MLflow** (3.2+) with `MLFLOW_ENABLE_OTEL_GENAI_SEMCONV=true`
- **Envoy AI Gateway** with AI/LLM metrics enabled
- Any OTel-instrumented inference stack exporting via OTLP

Prometheus converts the OTel histogram name from
`gen_ai.client.token.usage` to `gen_ai_client_token_usage`
(dots to underscores). The `_sum` suffix provides the
cumulative token count.

### Kuadrant identity-based (second fallback)

| Metric | Prometheus source | What it measures |
|--------|------------------|------------------|
| Token hits | `authorized_hits` | Total tokens consumed per user/organization |

Grouped by `limitador_namespace`, `organization`, and `user`.

These metrics come from Kuadrant Limitador's
`authorized_hits` counter, populated via TelemetryPolicy
with `auth.identity` selectors. Labels are derived from
Keycloak JWT claims injected by Authorino as HTTP headers:

- **organization** from `X-Organization` header (mapped
  from `auth.identity.realm_access.organization` or similar
  JWT claim)
- **user** from `X-Remote-User` header (mapped from
  `auth.identity.sub` JWT claim)

**When it is used:** shared model endpoints fronted by
Connectivity Link (Kuadrant) where tokens are attributed by
user identity (API key / JWT) rather than by pod/namespace.
This is common in multi-tenant inference gateways where
multiple users share the same vLLM deployment.

**Prerequisites:**
- Kuadrant Connectivity Link deployed with Limitador
- TelemetryPolicy configured with `auth.identity` selectors
  that map JWT claims to `organization` and `user` labels
- Authorino injecting identity headers (`X-Organization`,
  `X-Remote-User`) from Keycloak token introspection
- Prometheus scraping Limitador metrics

**Note:** `authorized_hits` tracks total tokens consumed
(not split by input/output). All hits are recorded as input
populated only when this source is active.

### Fallback Logic

The operator tries vLLM metrics first. If both input and
output token queries return empty results, it falls back to
OTel GenAI metrics. If those also return empty, it falls
back to Kuadrant identity-based metrics. All three produce
the same CSV format.

```
1. Query vllm:prompt_tokens_total → results?
   ├── yes → use vLLM metrics
   └── no → Query gen_ai_client_token_usage_sum → results?
            ├── yes → use OTel metrics
            └── no → Query authorized_hits → use Kuadrant identity metrics
```

## CSV Report Format

The operator produces a monthly CSV file alongside existing
reports (CPU, memory, storage, GPU):

**Filename:** `cm-openshift-inference-token-usage-YYYYMM.csv`

| Column | Type | Description |
|--------|------|-------------|
| `report_period_start` | timestamp | Start of the reporting period |
| `report_period_end` | timestamp | End of the reporting period |
| `interval_start` | timestamp | Start of the collection interval |
| `interval_end` | timestamp | End of the collection interval |
| `node` | string | Node running the inference pod |
| `namespace` | string | Kubernetes namespace |
| `pod` | string | Pod name |
| `model_name` | string | LLM model identifier (e.g., `llama-3-70b`) |
| `inference_service` | string | KServe InferenceService name (vLLM only) |
| `organization` | string | Organization from Kuadrant identity (identity metrics only) |
| `input_tokens` | numeric | Prompt tokens consumed in this interval |
| `output_tokens` | numeric | Generation tokens produced in this interval |

Note: `inference_service` is populated from the
`serving.kserve.io/inferenceservice` pod label when using
vLLM metrics. When using OTel GenAI metrics, this field
may be empty unless the OTel-instrumented app sets
equivalent metadata.

when using Kuadrant identity-based metrics. These values
come from TelemetryPolicy `auth.identity` selectors mapped
to Keycloak JWT claims.

## Prometheus Queries

### vLLM-native

```promql
# Input tokens per pod/namespace/node/model/service
sum by (exported_pod, exported_namespace, Hostname,
        model_name, label_serving_kserve_io_inferenceservice)(
  increase(vllm:prompt_tokens_total[1h])
  * on(exported_pod, exported_namespace)
    group_left(label_serving_kserve_io_inferenceservice)
    label_replace(label_replace(kube_pod_labels,
      'exported_pod', '$1', 'pod', '(.*)'),
      'exported_namespace', '$1', 'namespace', '(.*)')
)
```

### OTel GenAI standard

```promql
# Input tokens per pod/namespace/model (OTel convention)
sum by (namespace, pod, gen_ai_request_model)(
  gen_ai_client_token_usage_sum{gen_ai_token_type="input"}
)

# Output tokens per pod/namespace/model (OTel convention)
sum by (namespace, pod, gen_ai_request_model)(
  gen_ai_client_token_usage_sum{gen_ai_token_type="output"}
)
```

### Kuadrant identity-based

```promql
# Token hits per namespace/organization/user (Limitador)
sum by (limitador_namespace, organization, user)(
  authorized_hits
)
```

## How It Fits in the Pipeline

```
vLLM pods ──────────────┐
                        ├──► Prometheus ──► koku-metrics-operator ──► CSV ──► Koku
MLflow / Envoy AI ──────┤
Gateway / OTel apps     │
                        │
Kuadrant Limitador ─────┘
(authorized_hits)
```

The operator collects token metrics using the same
mechanism as CPU, memory, storage, and GPU metrics. The
CSV is uploaded to Cost Management (SaaS) or stored
locally (air-gapped/on-prem).
